### A1: Dependencies to Add to pom.xml

**Question:** The pom.xml has no JPA, Flyway, H2, or PostgreSQL dependencies. What exact blocks need to be added?

**Proposed Answer:**

All of the following should be added. Versions managed by Spring Boot 3.5.14 parent unless noted.

```xml

<dependency>

    <artifactId>spring-boot-starter-data-jpa</artifactId>

<dependency>
    <groupId>org.flywaydb</groupId>

    <groupId>org.flywaydb</groupId>

    <scope>runtime</scope>

<!-- H2 in-memory DB (local + test profiles) -->
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>

<!-- Jakarta Bean Validation -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

All versions are managed by the `spring-boot-starter-parent` 3.5.14 BOM. No explicit version
pins required.

### A3: AES-256-GCM Key Configuration for Local/Test

**Question:** Where should the test encryption key live to avoid secrets in committed files (Standard §25)?

**Proposed Answer:**

For `local` and `test` profiles, use a fixed, well-known test key set via `application-local.yml`
**only if that file is in `.gitignore`**. Checking the repo: `application-local.yml` is committed
(it currently contains only `spring.cloud.config.enabled: false`), so putting a key there would
violate Standard §25.

**Decision:** Use an environment variable `APP_ENCRYPTION_KEY` and bind via `@ConfigurationProperties`:

```yaml
# application-local.yml — safe to commit, no secret value
app:
  encryption:
    key: ${APP_ENCRYPTION_KEY:test-aes-256-key-32byteslong!!!!!}
```

The default fallback (`test-aes-256-key-32byteslong!!!!!`) is a well-known, non-secret test key
used only when the env var is absent — acceptable for local dev and unit tests. Production never
uses this profile. This satisfies Standard §25 (no real secret committed).

**Resolved:** Yes

### A4: H2 PostgreSQL Mode Compatibility with Flyway DDL

**Question:** Are there Flyway/DDL constructs in V1–V3 scripts that H2 does not support in `MODE=PostgreSQL`?

**Proposed Answer:**

Known compatibility considerations for H2 2.x in `MODE=PostgreSQL`:

| Construct | H2 Support in PostgreSQL mode | Decision |
|---|---|---|
| `TEXT` column type | Supported (maps to CLOB/VARCHAR internally) | Use `TEXT` — safe |
| `UUID` column type | Supported as of H2 2.x | Use `UUID` — safe |
| `gen_random_uuid()` as column default | **Not supported** in H2 | Avoid DB-level UUID defaults — generate UUID in Java (`UUID.randomUUID()`) |
| `CREATE TABLE IF NOT EXISTS` | Supported | Use for idempotency (Standard §21) |
| `CREATE INDEX IF NOT EXISTS` | Supported | Use for idempotency |
| `BIGSERIAL` / `SERIAL` | Use `BIGINT GENERATED ALWAYS AS IDENTITY` or `SERIAL` | Use `BIGINT GENERATED BY DEFAULT AS IDENTITY` — supported in both H2 and PG |
| `VARCHAR(n)` | Supported | Safe |

**Action:** DDL scripts must use Java-generated UUIDs (no `gen_random_uuid()` defaults). Use
`BIGINT GENERATED BY DEFAULT AS IDENTITY` for `ClientProfileEntity.id`. All other constructs
are compatible.

**Resolved:** Yes

## Domain B — Data

### B1: UUID @Id Generation Strategy (Hibernate 6)

**Question:** Correct `@GeneratedValue` strategy for UUID primary key under Hibernate 6 / Spring Boot 3.x?

**Proposed Answer:**

In Hibernate 6 (Spring Boot 3.x), `@GeneratedValue(strategy = GenerationType.AUTO)` with a
`UUID` field has changed behaviour — it delegates to Hibernate's UUID generator by default.
However the most explicit and portable approach is:

```java
@Id
@GeneratedValue(strategy = GenerationType.UUID)
@Column(updatable = false, nullable = false)
private UUID transactionId;
```

`GenerationType.UUID` was introduced in JPA 3.1 (Jakarta Persistence 3.1) and is the canonical
choice for UUID PKs in Hibernate 6+. This avoids the deprecated `@GenericGenerator` approach
and the ambiguity of `AUTO`.

**Resolved:** Yes

### B2: Spring-Managed AttributeConverter in @Embeddable

**Question:** Can Hibernate inject a Spring-managed `EncryptedStringConverter` `@Component` into an `@Embeddable` `PpiChangeRecord`?

**Proposed Answer:**

Yes — with the correct configuration. When `EncryptedStringConverter` is declared as:
- A Spring `@Component` (so it's in the Spring context)
- `@Converter(autoApply = false)` (so it doesn't auto-apply to all `String` fields globally)

And applied explicitly on the `@Embeddable` fields with `@Convert(converter = EncryptedStringConverter.class)`,
Hibernate will use Spring's `EntityManagerFactory` integration to look up the converter bean
from the application context — this works automatically with `spring-boot-starter-data-jpa`
because Spring Boot configures the `LocalContainerEntityManagerFactoryBean` with a
`SpringBeanContainerLifecycleStrategy` that bridges Hibernate's bean container to Spring's
`ApplicationContext`.

**No additional config needed** beyond having the converter be a `@Component` and using
`@Convert(converter = EncryptedStringConverter.class)` explicitly on each field.

**Resolved:** Yes

### B3: FraudAlert → Transaction FK Constraint

**Question:** Plain `@Column` UUID or DB-level FK to transaction table?

**Proposed Answer:**

**No FK constraint.** The `FraudAlert` is intentionally decoupled from `Transaction` to allow:
- Independent query paths (alerts can outlive audit-purged transactions)
- No cascade complications
- Simpler eventual-consistency model when alerts are created from event streams

The Flyway V3 DDL will declare `transaction_id UUID NOT NULL` as a plain column.
An index on `transaction_id` is still useful for query performance.

**Resolved:** Yes

### B4: @CollectionTable Config for ppiChangeHistory

**Question:** What is the correct `@CollectionTable` config for `ClientProfileEntity.ppiChangeHistory`?

**Proposed Answer:**

```java
@ElementCollection(fetch = FetchType.LAZY)
@CollectionTable(
    name = "client_profile_ppi_change",
    joinColumns = @JoinColumn(name = "client_profile_id"))
@OrderBy("change_date ASC")
private List<PpiChangeRecord> ppiChangeHistory = new ArrayList<>();
```

- Table name: `client_profile_ppi_change`
- Join column: `client_profile_id` (FK to `client_profile.id`)
- Fetch type: `LAZY` — avoids loading full history on every profile fetch
- `@OrderBy` ensures chronological order without requiring a separate sort in service code

**Resolved:** Yes

## Domain C — Architecture

### C1: Component Scanning — @EntityScan / @EnableJpaRepositories

**Question:** Will `@SpringBootApplication` at `za.co.capitecbank` pick up entities and repositories in sub-packages automatically?

**Proposed Answer:**

Yes. `@SpringBootApplication` includes `@ComponentScan(basePackageClasses = Application.class)`,
which scans `za.co.capitecbank` and all sub-packages recursively. JPA entities annotated with
`@Entity` and repositories extending `JpaRepository` in any sub-package (e.g.
`za.co.capitecbank.persistence.entity`, `za.co.capitecbank.persistence.repository`) will be
detected automatically.

**No `@EntityScan` or `@EnableJpaRepositories` annotation is needed** unless entities or
repositories are placed outside the `za.co.capitecbank` root package — which they are not.

**Resolved:** Yes

### C2: FraudPersistenceService Class Declaration Constraints

**Question:** Is "not final" the only constraint on the persistence service class?

**Proposed Answer:**

Yes, the only hard constraint is that `FraudPersistenceService` must **not** be declared `final`
(Standard §18 — `final` breaks Spring AOP CGLIB proxying, which is how `@Transactional` is
applied). All other `@Service` class rules apply normally:
- `@Slf4j`, `@Service`, `@RequiredArgsConstructor`
- Constructor injection only — no `@Autowired` fields
- No `extends` — composition only (Standard §18)

**Resolved:** Yes

### C3: Flyway vs ddl-auto for Local H2 Profile

**Question:** Should Flyway run against H2 locally, or use `ddl-auto: create-drop`?

**Proposed Answer:**

**Flyway must run even locally** (Standard §21 mandates Flyway — no exceptions). Using
`ddl-auto: create-drop` bypasses migration scripts and would diverge schema from production,
defeating the purpose of Flyway.

Configuration in `application-local.yml`:
```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
  jpa:
    hibernate:
      ddl-auto: none   # Flyway owns schema — Hibernate must not interfere
    show-sql: false
```

`ddl-auto: none` is the correct companion to Flyway. Never use `create`, `create-drop`, or
`update` alongside Flyway (Standard §21 + §14).

**Resolved:** Yes

### C4: EncryptedStringConverter Spring Injection Wiring

**Question:** How to wire `EncryptedStringConverter` as a Spring bean without `autoApply = true`?

**Proposed Answer:**

Use `@Converter(autoApply = false)` (explicit — only activates where `@Convert` is declared):

```java
@Converter(autoApply = false)   // do NOT auto-apply to all String fields
@Component
@RequiredArgsConstructor
public class EncryptedStringConverter implements AttributeConverter<String, String> {

    private final FieldEncryptionService fieldEncryptionService;

    @Override
    public String convertToDatabaseColumn(final String plaintext) {
        if (plaintext == null) {
            return null;
        }
        return fieldEncryptionService.encrypt(plaintext);
    }

    @Override
    public String convertToEntityAttribute(final String ciphertext) {
        if (ciphertext == null) {
            return null;
        }
        return fieldEncryptionService.decrypt(ciphertext);
    }
}
```

Then apply explicitly on PII fields only:
```java
@Convert(converter = EncryptedStringConverter.class)
@Column(name = "full_name")
private String fullName;
```

Spring Boot's JPA autoconfiguration registers all `@Component` converters in the Hibernate
bean container automatically — no manual `@Bean` registration in a `@Configuration` class is
needed.

**Resolved:** Yes
